# 快手小店第7张表审核草稿：`kuaishouxiaodian.weekly_refunds`

> 状态：已确认、已建表、已上传数据、已校验通过  
> 数据库：`weidian`  
> Schema：`kuaishouxiaodian`  
> 表序号：07 / 35  
> 数据来源：`kuaishouxiaodian.raw_data`  
> 当前说明：原始文件没有独立退款金额列，本表必须结合`售后状态`、`实付款`和`订单备注`计算退款金额。

## 1. 表的作用

`weekly_refunds`用于保存快手小店按自然周汇总的退款金额。一条记录代表一个完整的周一至周日周期。

本表是整体退款表，不是客户相关表，也不是商品相关表，因此：

- 不筛选`渠道 = '分销'`。
- 不要求`SKU编码`有值。
- 不按订单状态筛选。交易关闭、退款关闭或售后状态为空的订单，只要订单备注中存在真实的系统小额打款，也必须计入退款。
- 退款归属日期使用订单的交易日期，不使用备注中的实际打款日期。

## 2. 自然周定义

- 每周第一天：星期一。
- 每周最后一天：星期日。
- `period_start`必须是星期一。
- `period_end`必须等于`period_start + 6天`。
- 跨月、跨年时仍保存完整的自然周边界。

示例：

```text
订单交易日期：2025-03-01（星期六）
所属自然周：2025-02-24 至 2025-03-02
```

即使实际小额打款发生在2025-03-14，该退款仍按照订单交易日期2025-03-01归入2025-02-24至2025-03-02这一周。

## 3. 数据粒度与唯一性

- 一条记录代表一个自然周的整体退款金额。
- 主键：`id`。
- 业务唯一键：`period_start + period_end`。
- 同一个自然周只能存在一条记录。
- 某个自然周没有任何退款金额时，不主动生成金额为0的记录。

## 4. 字段设计

本表严格保留以下6个字段：

| 序号 | 字段 | PostgreSQL类型 | 是否必填 | 默认值 | 说明 |
|---:|---|---|---|---|---|
| 1 | `id` | `BIGINT` | 是 | 自增 | 主键，由数据库自动生成 |
| 2 | `period_start` | `DATE` | 是 | 无 | 自然周开始日期，必须是星期一 |
| 3 | `period_end` | `DATE` | 是 | 无 | 自然周结束日期，必须是星期日 |
| 4 | `weekly_refund_amount` | `NUMERIC(18,2)` | 是 | `0` | 该自然周内各订单退款金额之和 |
| 5 | `created_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 首次插入数据库的北京时间 |
| 6 | `updated_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 最近刷新该记录的北京时间 |

## 5. 原始字段映射

| 计算用途 | `raw_data`原始字段 | 处理方式 |
|---|---|---|
| 订单业务键 | `订单号` | 同一订单内识别和去重退款记录 |
| 交易日期 | `订单创建时间` | 转换为北京时间日期，再确定所属自然周 |
| 整单金额 | `实付款` | 售后成功且没有部分退款证据时，作为整单退款金额 |
| 售后结果 | `售后状态` | 识别`退款成功`；不能单独决定所有退款金额 |
| 退款明细 | `订单备注` | 识别系统小额打款、明确部分退款金额和异常备注 |

原始字段`订单状态`只用于辅助审核，不作为本表的筛选条件。

## 6. 中间字段`refund_amount`

为了兼容其他平台，本表计算过程中统一生成订单级中间字段`refund_amount`，但不改变`raw_data`的67字段结构，也不新增永久中间表。

```text
raw_data原始记录
→ 按订单计算临时字段refund_amount
→ 按订单交易日期换算自然周
→ 汇总为weekly_refund_amount
```

`refund_amount`只存在于本表生成过程的查询中；最终`weekly_refunds`仍严格保留第4节列出的6个字段。

## 7. 订单退款金额计算优先级

同一订单严格按照以下顺序判断，命中前一条后不再叠加后续规则，避免重复计算。

### 7.1 第一优先级：系统“小额打款金额”

只要`订单备注`出现系统记录`小额打款金额¥ 数值`，就以实际小额打款记录为准，不再使用售后状态推算整单退款。

处理规则：

1. 从全部订单中识别系统小额打款，不预先筛选`售后状态`。
2. 提取小额打款记录中的系统时间戳和金额。
3. 按`订单号 + 系统时间戳 + 金额`去重。
4. 同一订单有多次不同时间的小额打款时，将全部真实打款金额求和。
5. 备注中同时出现“已退差价28”和“小额打款金额¥ 28”时，只计系统小额打款28，不再次叠加文字描述中的28。
6. 即使`售后状态`为`空白`、`退款关闭`或`换货成功`，只要存在真实小额打款，仍计入退款。

### 7.2 第二优先级：明确完成的部分退款

订单没有系统小额打款，但备注中明确记录已经完成的差价退款、运费退款或补偿时，使用备注中能够唯一确认的实际金额。

可自动采用金额必须同时满足：

- 备注表达的是已经完成，而不是“待回复”“协商”“可以退”等意向。
- 能提取到唯一明确的金额。
- 没有两个相互冲突的金额。
- 金额大于0。
- 金额没有无法解释的明显异常。

最终执行时采用以下确定规则：

- 退款成功且备注中只有一个明确金额时，使用该明确金额。
- 退款成功但备注金额缺失或存在多个冲突金额时，不猜测备注金额，回到平台权威状态口径，使用`实付款`。
- 售后状态不是退款成功时，只有“金额唯一且备注存在已退款、已打款或已补偿证据”才使用该金额；否则按0处理。
- 订单`2620600324860758`的备注明确写有“已退差价20”，原实付款为19.80，最终按原始明确退款金额20.00保留，并作为唯一一笔退款金额略高于实付款的已说明记录。

### 7.3 第三优先级：售后成功的整单退款

满足以下任一情况时，订单退款金额等于`实付款`：

- 没有系统小额打款、没有唯一明确部分退款金额，并且`售后状态 = '退款成功'`。
- 备注出现多个相互冲突的金额，但平台最终`售后状态 = '退款成功'`。

`仅退款`表示退款方式，并不自动等于部分退款。如果备注只有“仅退款”而没有差价、运费或部分退款语义，且售后状态为退款成功，则仍按整单`实付款`计算。

### 7.4 第四优先级：无退款

不符合前三类规则的订单，临时字段`refund_amount = 0`，不进入周退款汇总。

## 8. 不同退款证据的处理对照

| 订单情况 | `refund_amount`处理 |
|---|---|
| 有系统小额打款 | 累加去重后的真实小额打款金额 |
| 无小额打款，备注中有唯一且已完成的部分退款金额 | 使用明确部分退款金额 |
| 无小额打款、无部分退款语义，售后状态为退款成功 | 使用`实付款` |
| 仅出现“仅退款”，售后状态为退款成功 | 使用`实付款` |
| 有部分退款语义但金额缺失或冲突，售后状态为退款成功 | 使用`实付款`，不猜测备注金额 |
| 有部分退款语义但金额缺失或冲突，售后状态不是退款成功 | 退款金额为0 |
| 无实际退款证据且售后状态不是退款成功 | 退款金额为0 |

## 12. 拟执行建表SQL

```sql
CREATE TABLE kuaishouxiaodian.weekly_refunds (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    period_start DATE NOT NULL,
    period_end DATE NOT NULL,
    weekly_refund_amount NUMERIC(18,2) NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT weekly_refunds_period_check CHECK (
        EXTRACT(ISODOW FROM period_start) = 1
        AND period_end = period_start + 6
    ),
    CONSTRAINT weekly_refunds_positive_amount_check CHECK (
        weekly_refund_amount > 0
    ),
    CONSTRAINT weekly_refunds_period_uk UNIQUE (period_start, period_end)
);
```

## 13. 数据生成逻辑

完成订单级`refund_amount`解析和异常审核后，再执行自然周汇总：

```sql
SELECT
    transaction_date
        - (EXTRACT(ISODOW FROM transaction_date)::INTEGER - 1)
        AS period_start,
    transaction_date
        - (EXTRACT(ISODOW FROM transaction_date)::INTEGER - 1)
        + 6
        AS period_end,
    SUM(refund_amount)::NUMERIC(18,2)
        AS weekly_refund_amount
FROM resolved_order_refunds
WHERE refund_amount > 0
GROUP BY period_start, period_end
ORDER BY period_start;
```

这里的`resolved_order_refunds`表示同一事务中已经通过规则和异常复核的订单级临时结果，不是要新增的永久数据库表。

## 14. 原子建表与上传流程

1. 从`raw_data`读取`订单号`、`订单创建时间`、`实付款`、`订单状态`、`售后状态`和`订单备注`。
2. 按第7节优先级生成每个订单的临时`refund_amount`。
3. 检查金额缺失、金额冲突、完成语义及特殊表达式，并按第7节确定规则生成唯一结果。
4. 先执行只读预演，确认小额打款覆盖率、特殊订单和总金额。
5. 预演全部通过后，开启PostgreSQL事务并将事务时区设为`Asia/Shanghai`。
6. 创建`kuaishouxiaodian.weekly_refunds`。
7. 将订单交易日期换算为完整自然周，按周汇总正数退款金额。
8. 校验字段数、记录数、自然周边界、唯一性、金额和真实样例。
9. 校验所有订单级退款金额之和等于所有周退款金额之和。
10. 全部通过后提交；任一环节失败则回滚建表和全部数据写入。

这符合“一次性全部上传成功，或者一次性全部上传失败”的要求。

## 15. 后续原始数据变动时的刷新逻辑

订单备注和售后状态可能在订单创建数日后发生变化，因此刷新时必须根据发生变化的订单重新定位其原始交易日期所属自然周。

```text
raw_data订单新增或更新
→ 重新计算受影响订单的refund_amount
→ 根据订单创建时间定位受影响自然周
→ 重新汇总这些自然周内的全部订单退款
→ 替换weekly_refunds中对应自然周记录
→ 校验通过后与原始数据变动一起提交
→ 任一步失败则全部回滚
```

实际打款日期只用于识别和去重，不改变退款归属的交易周。
