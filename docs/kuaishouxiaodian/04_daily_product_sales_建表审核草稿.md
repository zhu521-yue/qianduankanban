## 1. 表的作用

`daily_product_sales`用于保存快手小店每个商品在每个自然日的购买金额和购买数量。一条记录代表“一个交易日期 + 一个SKU编码”的汇总结果，供商品销售趋势、商品排行以及后续周、月、季度、半年商品销售额表使用。

## 2. 数据粒度与唯一性

- 一条记录代表一个SKU编码在一个自然日内的有效销售汇总。
- 先按北京时间交易日期分组，再按SKU编码分组。
- 主键：`id`。
- 业务唯一键：`transaction_date + product_code`。
- 同一交易日期、同一SKU编码只能存在一条记录。
- 没有有效销售的日期或商品不生成补零记录。

## 3. 字段设计

本表严格保留以下7个字段：

| 序号 | 字段 | PostgreSQL类型 | 是否必填 | 默认值 | 说明 |
|---:|---|---|---|---|---|
| 1 | `id` | `BIGINT` | 是 | 自增 | 主键，由数据库自动生成 |
| 2 | `transaction_date` | `DATE` | 是 | 无 | `订单创建时间`对应的北京时间日期 |
| 3 | `product_code` | `TEXT` | 是 | 无 | 只使用去除首尾空格后的`SKU编码` |
| 4 | `transaction_amount` | `NUMERIC(18,2)` | 是 | `0` | 同日同SKU有效记录的`实付款`合计 |
| 5 | `product_quantity` | `BIGINT` | 是 | `0` | 同日同SKU有效记录的`成交数量`合计 |
| 6 | `created_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 首次插入数据库的北京时间 |
| 7 | `updated_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 最近刷新该记录的北京时间 |

## 4. 原始字段映射

| 目标内容 | `raw_data`原始字段 | 处理方式 |
|---|---|---|
| 交易日期 | `订单创建时间` | 转换为北京时间后取日期部分 |
| 有效销售判断 | `订单状态` | 仅保留`交易成功`、`已发货`、`已收货` |
| 商品编码 | `SKU编码` | 去除首尾空格；为空则该记录不进入本表 |
| 交易金额 | `实付款` | 按交易日期和SKU编码求和 |
| 商品数量 | `成交数量` | 按交易日期和SKU编码求和 |
| 售后信息 | `售后状态` | 本表不直接扣减；退款由后续退款相关表处理 |

`商品ID`不参与`product_code`计算，也不作为SKU编码为空时的备用值。

## 5. 有效销售与金额口径

第四张表沿用已经确认并上传的第三张表订单状态和金额口径：

- 纳入`交易成功`、`已发货`、`已收货`。
- 排除`交易关闭`、`待付款`、`待发货`、空状态和其他未确认状态。
- `transaction_amount`汇总原始字段`实付款`，保存毛销售额。
- 不根据`售后状态`直接删除订单或扣减退款。
- 后续需要商品净销售额时，再使用商品销售额减对应商品退款金额。

第四张表在上述订单状态规则之外，再增加一条商品有效性规则：`SKU编码`必须有值。

## 6. SKU编码处理逻辑

### 6.1 最终规则

```sql
NULLIF(BTRIM("SKU编码"::text), '') AS product_code
```

- SKU编码有值：去除首尾空格后作为`product_code`。
- SKU编码为`NULL`、空字符串或仅包含空格：该原始记录判为无效商品销售记录，不进入`daily_product_sales`。
- 即使该记录存在`商品ID`，也不使用商品ID代替SKU编码。
- “作废”只表示不进入第四张及后续商品维度表；原始记录仍保留在`raw_data`，不会删除或修改原始数据。

## 10. 拟执行建表SQL

```sql
CREATE TABLE kuaishouxiaodian.daily_product_sales (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    transaction_date DATE NOT NULL,
    product_code TEXT NOT NULL,
    transaction_amount NUMERIC(18,2) NOT NULL DEFAULT 0,
    product_quantity BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT daily_product_sales_date_product_uk
        UNIQUE (transaction_date, product_code)
);
```

## 11. 首次数据生成SQL

```sql
INSERT INTO kuaishouxiaodian.daily_product_sales (
    transaction_date,
    product_code,
    transaction_amount,
    product_quantity
)
SELECT
    ("订单创建时间" AT TIME ZONE 'Asia/Shanghai')::date AS transaction_date,
    BTRIM("SKU编码"::text) AS product_code,
    SUM("实付款")::NUMERIC(18,2) AS transaction_amount,
    SUM("成交数量")::BIGINT AS product_quantity
FROM kuaishouxiaodian.raw_data
WHERE "订单状态" IN ('交易成功', '已发货', '已收货')
  AND NULLIF(BTRIM("SKU编码"::text), '') IS NOT NULL
GROUP BY
    ("订单创建时间" AT TIME ZONE 'Asia/Shanghai')::date,
    BTRIM("SKU编码"::text)
ORDER BY transaction_date, product_code;
```

## 12. 原子建表与上传流程

1. 开启PostgreSQL事务，并将事务时区设为`Asia/Shanghai`。
2. 创建`kuaishouxiaodian.daily_product_sales`。
3. 从`raw_data`筛选`交易成功`、`已发货`、`已收货`记录。
4. 作废SKU编码为空的记录，不写入第四张表。
5. 将`订单创建时间`转换为北京时间交易日期。
6. 去除SKU编码首尾空格，作为`product_code`。
7. 按交易日期和商品编码分组，对`实付款`和`成交数量`求和。
8. 写入日商品销售额记录。
9. 校验字段数、联合唯一性、记录数、日期范围、金额和数量。
10. 核对与第三张表的8个预期差异日期及6,983.33差额。
11. 全部通过后提交；任一步失败则回滚建表和全部数据写入。

## 13. 后续原始数据变动时的刷新逻辑

以后每次新文件上传成功后，在同一次事务中重新计算受影响的交易日期：

```text
raw_data新增或更新成功
→ 找出受影响的北京时间交易日期
→ 删除daily_product_sales中这些日期的旧汇总记录
→ 排除这些日期中SKU编码为空的记录
→ 使用剩余有效SKU记录重新汇总
→ 写入新的日期+SKU结果
→ 校验通过后一起提交；失败则一起回滚
```

按整日删除后重建，可以正确处理同一天新增商品、SKU编码发生变化以及金额或数量被修改的情况，避免遗留旧商品记录。

当前`raw_data`允许保留重复原始记录，因此第四张表也会逐条统计`raw_data`中的有效SKU记录，不额外按订单号去重。
