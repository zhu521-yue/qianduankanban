## 1. 表的作用

`daily_sales`用于保存快手小店按交易日期汇总后的日销售额。一条记录代表一个自然日，供后续周、月、季度、半年销售额表以及销售趋势看板使用。

## 2. 数据粒度与唯一性

- 一条记录代表一个自然日的有效销售汇总。
- 交易日期按北京时间从`订单创建时间`提取。
- 主键：`id`。
- 业务唯一键：`transaction_date`。
- 同一个交易日期在本表中只能存在一条记录。
- 没有有效销售订单的日期不生成记录，不主动补零。

## 3. 字段设计

本表严格保留以下5个字段：

| 序号 | 字段 | PostgreSQL类型 | 是否必填 | 默认值 | 说明 |
|---:|---|---|---|---|---|
| 1 | `id` | `BIGINT` | 是 | 自增 | 主键，由数据库自动生成 |
| 2 | `transaction_date` | `DATE` | 是 | 无 | 交易日期，即订单创建时间对应的北京时间日期 |
| 3 | `transaction_amount` | `NUMERIC(18,2)` | 是 | `0` | 当日有效订单的`实付款`合计 |
| 4 | `created_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 首次插入数据库的北京时间 |
| 5 | `updated_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 最近刷新该记录的北京时间 |

## 4. 原始字段映射

| 目标内容 | `raw_data`原始字段 | 处理方式 |
|---|---|---|
| 交易日期 | `订单创建时间` | 转换为北京时间后取日期部分 |
| 订单是否属于有效销售 | `订单状态` | 暂定仅保留`交易成功`、`已发货`、`已收货` |
| 交易金额 | `实付款` | 按交易日期求和，保留两位小数 |
| 售后信息 | `售后状态` | 本表不扣减；退款数据由后续退款相关表单独处理 |

## 5. 有效销售口径

### 5.1 暂定纳入的订单状态

- `交易成功`
- `已发货`
- `已收货`

### 5.2 暂定排除的订单状态

- `交易关闭`
- `待付款`
- `待发货`
- 空值或其他未确认状态

采用这个口径的原因：`2026-07-28`的204条订单当前全部为`已发货`，若只统计`交易成功`，当天销售额会错误地变为0；`2026-07-01`也有2条`已收货`订单。因此，建议把`已发货`和`已收货`与`交易成功`一并认定为有效销售。

### 5.3 退款处理

本表记录有效订单的毛销售额，不根据`售后状态`直接删除或扣减订单：

- `transaction_amount`始终汇总原始字段`实付款`。
- 退款金额后续写入退款相关表中的`refund_amount`。
- 看板需要净销售额时，再使用“销售额减退款额”的展示口径。
- 这样可以保留原销售事实，也不会因为快手备注中部分退款金额难以识别而破坏本表结构。

## 9. 拟执行建表SQL

```sql
CREATE TABLE kuaishouxiaodian.daily_sales (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    transaction_date DATE NOT NULL,
    transaction_amount NUMERIC(18,2) NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT daily_sales_transaction_date_uk UNIQUE (transaction_date)
);
```

## 10. 首次数据生成SQL

```sql
INSERT INTO kuaishouxiaodian.daily_sales (
    transaction_date,
    transaction_amount
)
SELECT
    ("订单创建时间" AT TIME ZONE 'Asia/Shanghai')::date AS transaction_date,
    SUM("实付款")::NUMERIC(18,2) AS transaction_amount
FROM kuaishouxiaodian.raw_data
WHERE "订单状态" IN ('交易成功', '已发货', '已收货')
GROUP BY ("订单创建时间" AT TIME ZONE 'Asia/Shanghai')::date
ORDER BY transaction_date;
```

## 11. 原子建表与上传流程

1. 开启PostgreSQL事务，并将事务时区设为`Asia/Shanghai`。
2. 创建`kuaishouxiaodian.daily_sales`。
3. 从`raw_data`筛选有效销售状态。
4. 将`订单创建时间`转换为北京时间的交易日期。
5. 按交易日期分组，对`实付款`求和。
6. 写入日销售额记录。
7. 校验字段数、日期唯一性、记录数、日期范围和总金额。
8. 全部通过后提交事务；任一步失败则回滚建表和全部数据写入。

## 12. 后续原始数据变动时的刷新逻辑

以后每次新文件上传成功后，在同一次上传事务中重新计算受影响交易日期：

```text
raw_data新增或更新成功
→ 找出受影响的北京时间交易日期
→ 使用raw_data中该日期的全部记录重新汇总
→ 按transaction_date更新或插入daily_sales
→ 校验通过后一起提交；失败则一起回滚
```

- 新日期：插入一条日销售额记录。
- 已存在日期：重新汇总该日全部有效订单，更新`transaction_amount`和`updated_at`。
- 同一原始订单即使在`raw_data`中重复出现，也会按原始记录逐条计入；当前`raw_data`不以订单号去重，这与已确认的原始表规则保持一致。
