## 1. 表的作用

`daily_customer_sales`用于保存快手小店每个客户在每个自然日的交易金额。一条记录代表“一个交易日期 + 一个客户ID”的销售汇总，供日客户排行、客户销售趋势和后续客户相关汇总表使用。

## 2. 数据粒度与分组顺序

- 一条记录代表一个客户在一个自然日内的有效销售汇总。
- 本表先按交易日期分组，再按客户ID分组。
- 主键：`id`。
- 业务唯一键：`transaction_date + customer_id`。
- 同一交易日期、同一客户ID只能存在一条记录。
- 没有有效销售的日期或客户不生成补零记录。

说明：后续`customer_daily_sales`虽然字段和结果与本表一致，但业务描述中的分组顺序是先客户ID、再交易日期；本表顺序是先交易日期、再客户ID。

## 3. 字段设计

本表严格保留以下6个字段：

| 序号 | 字段 | PostgreSQL类型 | 是否必填 | 默认值 | 说明 |
|---:|---|---|---|---|---|
| 1 | `id` | `BIGINT` | 是 | 自增 | 主键，由数据库自动生成 |
| 2 | `transaction_date` | `DATE` | 是 | 无 | `订单创建时间`对应的北京时间日期 |
| 3 | `customer_id` | `TEXT` | 是 | 无 | 按CPS达人ID、团长ID、快赚客ID的优先级解析 |
| 4 | `transaction_amount` | `NUMERIC(18,2)` | 是 | `0` | 同日同客户有效订单的`实付款`合计 |
| 5 | `created_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 首次插入数据库的北京时间 |
| 6 | `updated_at` | `TIMESTAMPTZ` | 是 | `CURRENT_TIMESTAMP` | 最近刷新该记录的北京时间 |

## 4. 原始字段映射

| 目标内容 | `raw_data`原始字段 | 处理方式 |
|---|---|---|
| 交易日期 | `订单创建时间` | 转换为北京时间后取日期部分 |
| 客户渠道 | `渠道` | 去除首尾空格后只保留`分销` |
| 有效销售判断 | `订单状态` | 仅保留`交易成功`、`已发货`、`已收货` |
| 客户ID | `CPS达人ID`、`团长ID`、`快赚客ID` | 按已确认的三级优先级选择 |
| 交易金额 | `实付款` | 按交易日期和客户ID求和 |
| 售后信息 | `售后状态` | 本表不直接扣减；退款由后续退款相关表处理 |

本表不需要商品编码，因此第四张商品表的“空SKU作废”规则不作用于本表。只有`渠道 = '分销'`、订单状态有效且能解析出客户ID的记录，才参与客户日销售额计算。

## 5. 有效销售与金额口径

第五张表沿用已经确认并上传的第三张表口径：

- 首先筛选`BTRIM("渠道"::text) = '分销'`。
- 纳入`交易成功`、`已发货`、`已收货`。
- 排除`交易关闭`、`待付款`、`待发货`、空状态和其他未确认状态。
- `transaction_amount`汇总原始字段`实付款`，保存毛销售额。
- 不根据`售后状态`直接删除订单或扣减退款。
- 后续计算客户净销售额时，再使用客户销售额减对应客户退款金额。

## 6. 客户ID计算逻辑

客户ID规则与第二张`customer_id_mapping`完全一致：

在执行以下客户ID解析前，必须先筛选`渠道 = '分销'`；非分销渠道不参与客户ID计算。

```sql
CASE
    WHEN NULLIF(BTRIM("CPS达人ID"::text), '') IS NOT NULL
        THEN BTRIM("CPS达人ID"::text)
    WHEN NULLIF(BTRIM("团长ID"::text), '') IS NOT NULL
        THEN BTRIM("团长ID"::text)
    WHEN NULLIF(BTRIM("快赚客ID"::text), '') IS NOT NULL
        THEN BTRIM("快赚客ID"::text)
    ELSE NULL
END AS customer_id
```

具体规则：

1. CPS达人ID有值时，使用CPS达人ID。
2. CPS达人ID为空、团长ID有值时，使用团长ID。
3. CPS达人ID和团长ID都为空、快赚客ID有值时，使用快赚客ID。
4. 三类客户ID都为空时，该分销记录不进入第五张表。
5. 非分销渠道记录无论是否存在客户ID，都不进入第五张表。
6. 客户昵称不写入本表，需要展示昵称时通过`customer_id_mapping`查询。

## 11. 首次数据生成SQL

```sql
WITH resolved AS (
    SELECT
        ("订单创建时间" AT TIME ZONE 'Asia/Shanghai')::date AS transaction_date,
        CASE
            WHEN NULLIF(BTRIM("CPS达人ID"::text), '') IS NOT NULL
                THEN BTRIM("CPS达人ID"::text)
            WHEN NULLIF(BTRIM("团长ID"::text), '') IS NOT NULL
                THEN BTRIM("团长ID"::text)
            WHEN NULLIF(BTRIM("快赚客ID"::text), '') IS NOT NULL
                THEN BTRIM("快赚客ID"::text)
            ELSE NULL
        END AS customer_id,
        "实付款" AS transaction_amount
    FROM kuaishouxiaodian.raw_data
    WHERE "订单状态" IN ('交易成功', '已发货', '已收货')
      AND BTRIM("渠道"::text) = '分销'
)
INSERT INTO kuaishouxiaodian.daily_customer_sales (
    transaction_date,
    customer_id,
    transaction_amount
)
SELECT
    transaction_date,
    customer_id,
    SUM(transaction_amount)::NUMERIC(18,2) AS transaction_amount
FROM resolved
WHERE customer_id IS NOT NULL
GROUP BY transaction_date, customer_id
ORDER BY transaction_date, customer_id;
```

SQL中的`BTRIM("渠道"::text) = '分销'`是所有客户相关表的统一前置筛选条件；`GROUP BY transaction_date, customer_id`对应本表“先交易日期、再客户ID”的分组描述。

## 12. 原子建表与上传流程

1. 开启PostgreSQL事务，并将事务时区设为`Asia/Shanghai`。
2. 创建`kuaishouxiaodian.daily_customer_sales`。
3. 从`raw_data`筛选`渠道 = '分销'`的记录。
4. 在分销记录中筛选有效销售状态。
5. 将`订单创建时间`转换为北京时间交易日期。
6. 按CPS达人ID、团长ID、快赚客ID的优先级解析客户ID。
7. 排除三类客户ID都为空的分销记录。
8. 先按交易日期分组，再按客户ID分组，对`实付款`求和。
9. 写入日客户销售额记录。
10. 校验字段数、联合唯一性、记录数、日期范围和总金额。
11. 检查全部客户ID都存在于第二张客户ID表。
12. 核对与第三张表的533个预期差异日期及544,554.81差额。
13. 全部通过后提交；任一步失败则回滚建表和全部数据写入。

## 13. 后续原始数据变动时的刷新逻辑

以后每次新文件上传成功后，在同一次事务中重新计算受影响的交易日期：

```text
raw_data新增或更新成功
→ 找出受影响的北京时间交易日期
→ 先更新customer_id_mapping
→ 删除daily_customer_sales中这些日期的旧汇总记录
→ 只保留渠道为分销的记录
→ 重新解析这些日期的客户ID并排除无客户ID记录
→ 按日期+客户ID重新汇总并写入
→ 校验通过后一起提交；失败则一起回滚
```

按整日删除后重建，可以正确处理同一天新增客户、客户ID来源变化以及交易金额被修改的情况，避免遗留旧客户记录。

当前`raw_data`允许保留重复原始记录，因此第五张表也会逐条统计`raw_data`中的有效客户记录，不额外按订单号去重。
