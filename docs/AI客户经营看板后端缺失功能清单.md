## 1. 审计结论

现有后端已经具备“数据库访问、平台映射、日期窗口、权限工具、Repository 和部分页面查询 Service”，并且连接当前数据库后能够返回真实结果。

现已通过 `backend/http.py` 将已经实现的8个查询能力暴露为 HTTP 接口，并提供健康检查、接口调试页、基础异常映射和服务启动入口。前端开发环境已经关闭 Mock，通过 Vite `/api` 代理读取真实数据库结果。

客户活跃度评分已完成私域组 / 分销组和达人组规则落地：`/api/customers/health-score` 返回单客户评分，`/api/customers/activity-summary` 返回组长端客户活跃程度汇总。更宽口径五维健康度已退出当前业务标准，不再列为待实现项。当前主要缺口集中在自定义趋势、上传链路、列表 / 详情补字段和数据契约；正式登录与强权限链路因内部使用场景调整为最后处理。

- 跟进状态。

销售金额、近7日、近30日排序已经由后端执行；其余筛选和排序仍会在前端明确提示暂不受支持。

### 4.2 客户详情字段

当前详情已返回：

- 平台、custom_id。
- 指定日销售金额/数量。
- 近7日销售金额/数量。
- 近30日销售金额/数量。
- 健康基础表原始字段。

缺失：

- 客户展示名称与 custom_id 的正式区分。
- 合作开始时间。
- 平均单次拿货金额。
- 同比、日环比、周环比和月环比。
- 客户活跃度得分和状态尚未内联到客户详情 DTO；当前可通过 `/api/customers/health-score` 单独查询。
- 风险原因、触发规则和建议动作。
- 跟进状态。
- 单客户日/周/月产品拿货趋势。

现有 `get_product_structure` 是平台/权限范围级产品结构，不能直接当作单客户产品趋势使用。

### 4.3 客户活跃度和客户分布

更宽口径五维健康度已退出当前业务标准，不再作为待实现功能跟进。

当前已实现的新口径：

- `/api/customers/health-score`：返回单客户客户活跃度评分。
- `/api/customers/activity-summary`：返回客户活跃程度状态汇总。
- 私域组 / 分销组：按前端选择的 day / week / month / custom 周期计算。
- 达人组：不论前端周期如何传入，固定按选定日期所属业务半年计算。

后续如需优化，仅考虑把客户活跃度状态直接内联到客户列表 / 客户详情 DTO，减少前端二次请求；不再补五维健康度逐项得分、扣分原因或健康等级公式。

### 4.4 自定义日期同比/环比

`custom_trend_metrics()` 当前主动返回 `RULE_PENDING`。

缺失：

- 自定义区间同比窗口。
- 上一周期环比窗口。
- 跨月、跨季度、半年比较适用规则。
- 无可比数据原因。

固定日期下已有数据库字段可以返回同比、日环比、周环比和月环比，但还需确认数据库比例是 `0.125` 还是 `12.5`。前端适配层目前做了临时数值归一化，正式接口应固定单位。

### 4.5 看板页面聚合 DTO

现有销售接口按平台返回，并提供授权平台合计。为了得到主管“整体 + 三个小组”，前端兼容层需要分别请求各小组。

建议后端增加页面聚合接口，一次返回：

- 渠道整体及三个小组。
- 当前小组整体及下属平台。
- 销售、趋势、客户分布模块状态。
- 部分成功信息。

这不是前端运行的绝对阻塞项，但会减少重复请求并统一页面口径。

## 7. P1：数据契约和精度问题

### 7.1 金额类型

当前 `payload.py` 将 Decimal 转为 float，Service 中也多次调用 `float()`。

风险：金额在 JSON 和前端中可能出现二进制浮点精度问题。

建议：API 金额统一返回两位小数字符串，或统一返回整数分。前端已经集中封装金额格式化，调整适配层即可。

### 7.2 日期范围返回

后端内部正确使用左闭右开区间，但自定义接口直接把 `window.end` 返回给前端，因此结束日期是用户选择日期的下一天。

建议：

- Repository/Service 内继续使用半开区间。
- HTTP DTO 对外返回用户输入的包含式 `start_date/end_date`。
- 如需暴露内部范围，单独命名 `exclusive_end`，避免误解。

### 7.3 名称统一

当前有以下差异：

- HTML 小组旧编码 `talent`，后端编码 `influencer`；前端工程已统一为 `influencer`。
- 后端显示名“聚水潭平台”，页面显示“聚水潭线上平台”。
- 客户表只有 `custom_id`，暂未明确其是否同时是页面客户名称。

应由元数据接口给出唯一展示名称和编码。

## 10. 当前前端对后端缺失的处理

| 后端缺失 | 前端当前处理 |
|---|---|
| HTTP 服务 | 已关闭 Mock，通过 Vite `/api` 代理读取真实数据库结果 |
| 无登录会话 | 内部使用阶段保留开发预览身份选择；正式登录和强权限链路最后处理 |
| 无元数据接口 | 使用与后端枚举一致的本地元数据 |
| 客户列表同比/环比、活跃状态内联和跟进指标缺失 | 显示“暂无”，活跃度可通过已实现接口单独查询或汇总 |
| 活跃/跟进筛选和同比/环比排序缺失 | 真实模式提示当前条件不受支持 |
| 五维健康度 | 已退出当前业务标准，不再显示 `RULE_PENDING` 作为待实现项 |
| 自定义趋势缺失 | 显示 `RULE_PENDING` |
| 单客户产品趋势缺失 | 不使用平台产品结构冒充，显示待实现 |
| 销售上传缺失 | 真实模式阻止提交并显示具体原因 |
| 上传记录缺失 | 显示空状态 |
| 数据最新日期缺失 | 显示“后端暂无最新日期接口” |

这样可以保证前端工程和页面先完成，同时不把任何演示计算误认为真实后端结果。
