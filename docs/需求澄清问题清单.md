- 角色：主管、组长。

1. 指标口径没有闭环。

## 0.1 前端展示结构与页面字段口径（开发对接版）

### 0.1.1 整体页面和权限结构

第一版是带固定账号权限的前端经营看板，展示层级为：

```text
主管
├── 私域组
│   ├── 有赞平台
│   └── 快团团平台
├── 达人组
│   ├── 抖音平台
│   ├── 快手小店
│   └── 微店
└── 分销组
    ├── 聚水潭线上平台
    └── 阿里巴巴平台
```

主管端初始页面：

```text
主管端
├── 渠道总览页
├── 私域组展示页
├── 达人组展示页
└── 分销组展示页
```

组展示页是页面集合 / 容器，内部包含：

```text
组展示页
├── 组别分析页
├── 客户列表页
└── 客户详情页
```

组长端页面：

```text
组长端
├── 自己小组的组别分析页
├── 自己小组的客户列表页
├── 自己小组的客户详情页
└── 数据上传页
    ├── 销售数据上传页
    └── 客户名单上传页
```

权限口径：

- 主管可查看渠道整体和三个组的数据；对销售数据和客户名单具有查看权限，但不能上传。
- 组长只能查看和上传自己所属小组的销售数据和客户名单。
- 主管和组长在各自权限范围内全部字段可见。
- 业务负责人维度暂定保留，但第一版不作为客户列表筛选项，也不强绑定核心指标。

### 0.1.6 数据上传页和上传记录字段

数据上传页只在组长端显示上传入口，主管端不显示上传入口；主管对销售数据和客户名单具有查看权限，但不能上传。

页面结构：

```text
数据上传页
├── 销售数据上传页
│   ├── 本组平台子页
│   └── 平台内上传入口
└── 客户名单上传页
    ├── 本组平台子页
    └── 平台内上传入口
```

上传权限：

- 组长只能上传自己小组范围内的销售数据和客户名单。
- 主管只能查看，不能上传。

上传粒度：

- 销售数据和客户名单都按平台粒度上传。
- 销售数据上传页展示当前组内各平台子页，并在平台子页内提供上传入口。
- 客户名单上传页展示当前组内各平台子页，并在平台子页内提供上传入口。
- 一个文件只对应一个平台。

销售数据处理边界：

- 后台一开始会处理历史销售数据。
- 前端上传入口只负责最新销售数据。
- 当日反复上传时，通过上传文件名计算哈希；哈希值相同则对当日上传数据执行覆盖。
- 销售数据上传页需要提示数据库已更新到某年某月某日的数据。

客户名单处理边界：

- 后台一开始会处理历史客户名单数据。
- 前端保留客户名单上传入口。
- 当日反复上传时，通过上传文件名计算哈希；哈希值相同则对当日上传数据执行覆盖。

通用上传规则：

- 支持 CSV 或 XLSX。
- 初始导入和后续上传复用同一套解析流程。
- 上传失败或字段不匹配时，需要展示错误行号和错误字段。

上传记录字段：

- 上传人。
- 上传时间。
- 平台。
- 文件名。
- 成功 / 失败状态。
- 数据类型

上传记录可见范围：

- 组长只能看自己上传记录。
- 主管可以看所有组上传记录。
- 不允许下载历史上传文件。
- 失败记录也保留。
- 日志记录超过 6 个月过期。

## 一、优先确认的核心问题

### P0-01：渠道 / 小组 / 平台的层级关系是什么？【已确认】

**已确认结论**

这是一个前端看板项目，当前展示层级确认如下：

```text
主管
├── 组长 / 小组 A
│   ├── 平台 A-1
│   ├── 平台 A-2
│   └── 平台 A-3
├── 组长 / 小组 B
│   ├── 平台 B-1
│   └── 平台 B-2
└── 组长 / 小组 C
    ├── 平台 C-1
    └── 平台 C-2
```

**看板展示规则**

- 组长视角：可以看到自己小组下各平台的信息，以及本小组的合计信息。
- 主管视角：可以看到各组长 / 各小组的信息，以及各小组的合计信息。
- 当前项目重点是前端看板展示，不先扩展成复杂组织管理系统。

**产品口径**

- “组长”是主管下的管理对象。
- “小组”是组长负责的数据范围。
- “平台”是组长 / 小组下面的二级统计维度。
- 主管端聚合维度：组长 / 小组。
- 组长端聚合维度：平台。

**仍需后续确认的边界**

- 一个组长是否只负责一个小组。
- 一个平台是否只能归属于一个组长 / 小组。
- 一个客户是否只能归属于一个平台。
- 一笔销售数据是否必须归属到唯一平台。

这些问题不影响前端看板第一层页面结构，但会影响后续数据清洗和指标归属。

**开发影响**

- 页面展示模块以 `项目框架.txt` 中各页面写明的模块为准，不做删减或重排。
- 主管页面展示维度：组长 / 小组。
- 组长页面展示维度：平台。

### P0-03：销售金额的统计口径是什么？【平台销售规则已补充】

> 当前状态：甲方已授权使用 `data/平台数据处理.txt` 作为平台销售数据处理依据。第一版按该文件中各平台“有用字段”先筛选字段，再按平台销售计算规则过滤数据并计算销售金额；日期统一格式化为 `yyyy-mm-dd`。

**已确认结论**

销售金额指标在页面展示上拆为四类周期：

```text
销售金额
├── 昨日销售金额
├── 近7日销售金额
├── 近30日销售金额
└── 自定义时间销售金额
```

这里的“四类销售金额”是展示周期拆分，不是四套不同指标。底层采用统一标准化结果字段，再按时间范围聚合。

**统一处理流程**

```text
原始 CSV / XLSX 文件
→ 按平台筛选“有用字段”
→ 按平台销售计算规则过滤订单
→ 按平台公式计算销售金额 / 商品数量

→ 输出统一销售事实数据
```

第一版标准化字段建议至少包含：

```text
platform
sales_date      # yyyy-mm-dd
sales_amount
product_code
product_quantity
customer_name / customer_key
group_type
source_fields   # 可选，用于保留平台原始字段映射
```

### P0-07：健康度评分和等级规则是什么？【客户活跃度规则已确认，宽口径健康度参数待确认】

**已确认展示周期**

健康度模块保留以下四类周期：

```text
昨日
近7日
近30日
自定义时间
```

每个周期均展示健康客户数、观察客户数、风险客户数、流失预警客户数，并覆盖整体、各组、各平台维度。

**本轮新增确认：私域组 / 分销组客户活跃度规则**

客户活跃度按 100 分制计算。私域组和分销组按前端筛选日期 / 时间段计算，支持日、周、月、自定义时间；达人组使用独立的业务半年规则，不套用私域组 / 分销组规则。

输入指标：

```text
week       # 周下单频率
month      # 月下单频率
last_order # 距离上一次下单时间，单位：自然日
```

子分规则：

| 指标 | 条件 | 分数 |
| --- | --- | ---: |
| week | `week >= 7` | 100 |
| week | `5 <= week < 7` | 80 |
| week | `3 <= week < 5` | 40 |
| week | `week < 3` | 20 |
| month | `month >= 30` | 100 |
| month | `20 <= month < 30` | 80 |
| month | `10 <= month < 20` | 40 |
| month | `month < 10` | 20 |
| last_order | `last_order <= 3` | 100 |
| last_order | `3 < last_order <= 7` | 90 |
| last_order | `7 < last_order <= 15` | 80 |
| last_order | `15 < last_order <= 30` | 70 |
| last_order | `30 < last_order <= 60` | 60 |
| last_order | `60 < last_order <= 90` | 50 |
| last_order | `last_order > 90` 或无历史下单记录 | 0 |

得分公式：

```text
日维度：customer_score = 0.4 * last_order_score + 0.3 * week_score + 0.3 * month_score
周维度：customer_score = week_score
月维度：customer_score = month_score
自定义时间段：customer_score = 0.5 * week_score + 0.5 * month_score
```

自定义时间段先计算所选时间范围内的周下单频率平均值，再计算月下单频率平均值。实现时下单为 0 的自然周 / 自然月也计入平均，避免只平均有订单周期导致活跃度虚高。

客户状态：

| 分数范围 | state |
| --- | --- |
| `customer_score >= 90` | 高活跃 |
| `80 <= customer_score < 90` | 活跃 |
| `70 <= customer_score < 80` | 稳定 |
| `60 <= customer_score < 70` | 观察 |
| `50 <= customer_score < 60` | 风险 |
| `40 <= customer_score < 50` | 流失预警 |
| `customer_score < 40` | 流失 |

**本轮新增确认：达人组客户活跃度规则**

达人组只看业务半年维度。业务半年定义如下：

```text
上半年：2 月 ~ 7 月
下半年：8 月 ~ 次年 1 月
```

业务季度口径同步确认，但当前客户活跃度不使用季度维度：

```text
第一季度：2 月 ~ 4 月
第二季度：5 月 ~ 7 月
第三季度：8 月 ~ 10 月
第四季度：11 月 ~ 次年 1 月
```

达人组三个平台为抖店、快手小店、微店。不论前端传入日、周、月还是自定义时间，后端只用传入日期判断所属业务半年，并取该半年内 6 个月的月度记录：

```text
count = 六个月月拿货次数之和
money = 六个月月拿货金额之和
customer_score = 0.4 * count_score + 0.6 * money_score
```

达人组 count 子分：

| 条件 | 分数 |
| --- | ---: |
| `count >= 4` | 100 |
| `count = 3` | 80 |
| `count = 1 或 2` | 60 |
| `count = 0` | 20 |

达人组 money 子分：

| 条件 | 分数 |
| --- | ---: |
| `money >= 550000` | 100 |
| `400000 <= money < 550000` | 80 |
| `200000 <= money < 400000` | 70 |
| `100000 <= money < 200000` | 60 |
| `50000 <= money < 100000` | 40 |
| `10000 <= money < 50000` | 20 |
| `money < 10000` | 10 |

达人组客户状态：

| 分数范围 | state |
| --- | --- |
| `customer_score >= 90` | 高活跃 |
| `80 <= customer_score < 90` | 活跃 |
| `70 <= customer_score < 80` | 稳定 |
| `50 <= customer_score < 70` | 观察 |
| `40 <= customer_score < 50` | 风险 |
| `20 <= customer_score < 40` | 流失预警 |
| `customer_score < 20` | 流失 |

达人组组长端展示客户活跃程度汇总时，先按所属业务半年筛选客户并逐客户计算活跃度，再按 state 汇总客户数；私域组 / 分销组则按前端筛选日期 / 时间段筛选客户并分类汇总。

**当前规则草案**

甲方授权使用 `客户健康度与跟进提醒规则.md` 作为规则框架依据。当前健康度采用 100 分制草案：

| 评分维度 | 权重 | 说明 |
| --- | ---: | --- |
| 销售金额表现 | 30 分 | 判断客户当前周期销售金额和历史表现是否稳定 |
| 拿货频次表现 | 25 分 | 判断拿货次数是否稳定或明显下降 |
| 最近一次拿货时间 | 20 分 | 判断客户是否长期未拿货，是否存在沉默或流失风险 |
| 产品结构健康度 | 15 分 | 判断是否持续拿主推产品、产品结构是否过于单一 |
| 同比 / 环比趋势 | 10 分 | 判断客户同比、环比是否明显增长或下滑 |

当前健康度等级草案：

| 等级 | 分数范围 | 业务含义 |
| --- | ---: | --- |
| 健康 | 80–100 分 | 近 30 天稳定拿货、销售金额环比持平或增长、主推产品持续拿货 |
| 观察 | 60–79 分 | 仍有拿货，但金额、频次或产品结构轻微下降 |
| 风险 | 40–59 分 | 近 30 天拿货明显下降，或近 14 天未拿货 |

健康度规则输出字段草案：

```text
客户 ID（数据字段到位后确认）
客户名称
健康度评分
健康度等级
扣分原因
风险原因
建议动作
```

**已解决的疑问**

- 健康度需要输出 0–100 分评分。
- 健康度分为健康、观察、风险、流失预警四个等级。

**甲方结论**

## 五、页面展示模块保留原则

`项目框架.txt` 中各页面写明的模块，是甲方要看的展示部分，不是开发可以随意合并、删除或后置的模块。

### 5.1 主管端展示模块

主管端包括：

```text
渠道总览页
私域组展示页
达人组展示页
分销组展示页
```

其中各组展示页是页面集合 / 容器，内部包含：

```text
组别分析页
客户列表页
客户详情页
```

页面内原始设计的展示模块需要保留，例如：

- 销售指标。
- 客户指标。
- 趋势指标。
- 健康度总览指标。
- 待跟进提醒。
- 客户列表。
- 客户详情。

### 5.2 组长端展示模块

组长端只能看到自己所属组的展示页集合，展示页内部包含：

```text
组别分析页
客户列表页
客户详情页
数据上传页
  ├── 销售数据上传页
  └── 客户名单上传页
```

其中 `项目框架.txt` 中写明的各类模块，是组长需要看到的页面内容；`data/对于各个平台的数据处理.txt` 补充确认的数据上传页，是组长端新增的上传入口。后续只补充口径，不改变已确认模块归属。

### 5.3 开发实现边界

开发侧可以做复用，但复用只发生在实现层：

- 可以复用时间规则。
- 可以复用数据清洗逻辑。
- 可以复用指标计算函数。
- 可以复用图表组件。
- 可以复用表格组件。

但这些复用不能改变产品展示结构：

```text
产品展示模块 = 按甲方页面设计保留
开发实现组件 = 在不改变展示模块的前提下复用
```
