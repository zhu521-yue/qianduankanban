# PR：客户状态规则配置与客户健康度联动

> 状态：已实施并完成自动化测试、接口联调与事务回滚验证  
> 数据库：PostgreSQL `weidian`  
> 实施范围：三张 public 配置表、后端读取/保存/事务同步、前端组内编辑保存、主管端移除该模块。

## 1. 需求目标

将看板“设置 → 客户状态规则”由当前只读展示改为可保存配置，并满足：

1. 客户状态只能是以下 7 种，顺序固定：

   1. 高活跃
   2. 活跃
   3. 稳定
   4. 观察
   5. 风险
   6. 流失预警
   7. 流失

2. 前端不能新增、删除、改名或调整客户状态顺序，只能编辑每种状态的：

   - `state_instructions`：状态说明；
   - `follow_up_action`：建议跟进动作。

3. 在 `weidian.public` 下建立 3 张独立的组级配置表：达人组、私域组、分销组各一张。
4. 用户点击“保存设置”后，后端根据当前登录账号所属组更新对应配置表。
5. 配置表更新成功后，后端根据 `customer_health_status`，同步更新该组对应客户健康度表中的说明和跟进内容。
6. 配置表更新与客户健康度表同步必须处于同一个数据库事务：任何一步失败，全部回滚，不能出现配置已保存但客户数据没有同步的状态。

## 2. 固定状态顺序

三张配置表严格使用相同的 7 个状态。由于用户指定配置表只有 6 个字段，不增加 `sort_order` 字段，因此顺序由前端和后端共同使用固定常量维护：

```text
高活跃 → 活跃 → 稳定 → 观察 → 风险 → 流失预警 → 流失
```

后端读取时不能直接依赖数据库默认顺序，也不能仅依赖自增 ID；应使用固定状态数组或 SQL `CASE` 排序。

后端保存时必须验证：

- 恰好提交 7 条；
- 不允许缺少状态；
- 不允许重复状态；
- 不允许出现第 8 种状态；
- 不允许修改状态名称；
- 返回前端时始终按上述顺序排列。

## 3. public 下的三张配置表

### 3.1 建议表名

| 业务组 | 建议表名 | 登录角色/group_key |
|---|---|---|
| 达人组 | `public.talent_customer_status_action` | `talent` |
| 私域组 | `public.private_customer_status_action` | `private` |
| 分销组 | `public.distribution_customer_status_action` | `distribution` |

以上表名已按本 PR 落库并由后端使用。

### 3.2 六个字段

每张表只包含用户指定的 6 个字段：

| 字段 | 建议类型 | 约束/用途 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `customer_health_status` | `VARCHAR(32)` | 非空、唯一，只能是固定 7 种状态之一 |
| `state_instructions` | `TEXT` | 非空，客户状态说明 |
| `follow_up_action` | `TEXT` | 非空，建议跟进动作 |
| `created_time` | `TIMESTAMPTZ` | 非空，默认 `CURRENT_TIMESTAMP`，首次创建后不随普通修改变化 |
| `updated_time` | `TIMESTAMPTZ` | 非空，默认 `CURRENT_TIMESTAMP`，每次保存时更新 |

建议约束：

- `PRIMARY KEY (id)`；
- `UNIQUE (customer_health_status)`；
- `CHECK (customer_health_status IN ('高活跃','活跃','稳定','观察','风险','流失预警','流失'))`。

建表后，每张表初始化 7 行，状态名称固定。后续保存采用按 `customer_health_status` 更新或 upsert，不提供删除接口。

### 4.3 已确认的同步范围

已确认：为保证配置保存后，组级页面、店铺页面、客户列表和客户详情都立即显示新内容，每次保存同时同步：

1. 对应的 1 张组级 `customer_health_detail`；
2. 对应业务组下存在的全部平台级健康度表；
3. 对应业务组下的全部店铺级 `customer_health_detail`。

例如达人组保存一次，需要更新：

```text
public.talent_customer_status_action
  ├─ daren.customer_health_detail
  ├─ doudian.half_year_customer_health
  ├─ weidian.customer_health_detail
  ├─ doudianChildren.customer_health_detail
  ├─ doudianKocotree.customer_health_detail
  └─ kuaishouxiaodian.customer_health_detail
```

如果只更新 `daren.customer_health_detail`，当前前端仍会从店铺级表读取旧说明，因此页面不会完整反映新配置。

## 5. 字段确认与映射

已确认：原需求中的跟进字段名是笔误。public 配置表和现有客户健康度表统一使用 `follow_up_action`，不新增、不重命名客户健康度表字段。

字段映射如下：

| public 配置表 | 现有客户健康度表 |
|---|---|
| `customer_health_status` | `customer_health_status` |
| `state_instructions` | `state_instructions` |
| `follow_up_action` | `follow_up_action` |
| `updated_time` | 同步时更新 `updated_at` |

前端继续显示“建议跟进动作”，保存内容直接写入配置表及健康度表的 `follow_up_action`。

## 6. 前端交互

### 6.1 展示

客户状态规则模块固定展示 7 行，顺序不可调整：

| 客户状态 | 状态说明 | 建议跟进动作 |
|---|---|---|
| 高活跃 | 可编辑 | 可编辑 |
| 活跃 | 可编辑 | 可编辑 |
| 稳定 | 可编辑 | 可编辑 |
| 观察 | 可编辑 | 可编辑 |
| 风险 | 可编辑 | 可编辑 |
| 流失预警 | 可编辑 | 可编辑 |
| 流失 | 可编辑 | 可编辑 |

客户状态列只读；状态说明和建议跟进动作可编辑。

### 6.2 保存

用户点击“保存设置”后：

1. 前端提交当前 7 条完整配置；
2. 保存过程中禁用重复点击；
3. 后端全部成功后显示“保存成功”；
4. 任一表更新失败则后端回滚，前端显示后端返回的失败原因；
5. 保存成功后重新请求一次规则接口，以数据库最终结果刷新页面。

### 6.3 权限

- 达人组账号只能读取和修改达人组配置表；
- 私域组账号只能读取和修改私域组配置表；
- 分销组账号只能读取和修改分销组配置表；
- 不能通过修改前端请求参数跨组更新；组别必须以后端登录 Cookie 中的角色为准。
- 主管端不提供客户状态规则/客户健康度设置模块，也不允许通过接口读取或保存三组规则。

## 7. 后端接口调整

沿用现有接口，不新增另一套重复接口：

### 7.1 读取配置

```http
GET /api/v1/settings/health-rules
```

普通组账号根据登录角色读取对应 public 配置表，并固定返回 7 条；主管账号返回 `groups: []`，主管前端不调用此接口。

实际返回结构：

```json
{
  "groups": [
    {
      "group_key": "talent",
      "group_name": "达人组",
      "editable": true,
      "items": [
        {
          "customer_health_status": "高活跃",
          "state_instructions": "……",
          "follow_up_action": "……"
        }
      ]
    }
  ]
}
```

### 7.2 保存配置

```http
PUT /api/v1/settings/health-rules
```

实际请求结构：

```json
{
  "rules": [
    {
      "customer_health_status": "高活跃",
      "state_instructions": "……",
      "follow_up_action": "……"
    }
  ]
}
```

实际请求必须包含完整 7 条，并按固定状态校验。后端不接受前端传入表名、schema 名或 group_key，以免越权更新。

## 8. 后端保存事务

一次保存的建议执行顺序：

```text
开始事务
  1. 从登录会话确定业务组
  2. 验证恰好包含固定 7 种状态
  3. 锁定并更新该组 public 配置表的 7 条记录
  4. 按 customer_health_status 更新对应组级 customer_health_detail
  5. 按 customer_health_status 更新该组全部平台级健康度表
  6. 按 customer_health_status 更新该组全部店铺级 customer_health_detail
  7. 所有语句成功后提交
任一步失败
  回滚全部更新
```

同步 SQL 的逻辑等价于：

```sql
UPDATE <目标schema>.customer_health_detail AS health
SET state_instructions = rules.state_instructions,
    follow_up_action = rules.follow_up_action,
    updated_at = CURRENT_TIMESTAMP
FROM public.<当前组配置表> AS rules
WHERE health.customer_health_status = rules.customer_health_status;
```

这里更新的是所有历史及当前健康度记录中相同状态的说明和动作，不修改客户分数、客户状态、周期、销售额或拿货次数。

## 9. “自动更新”的实现边界

本 PR 将“自动更新”理解为：用户从前端保存时，后端在同一个事务中更新配置表和全部目标健康度表。

默认不使用数据库触发器。因此：

- 通过前端/后端接口保存：会完整联动；
- 人工直接执行 SQL 修改 public 配置表：不会自动联动健康度表。

如果要求人工直接修改配置表时也必须自动同步，则应改为 PostgreSQL 触发器方案，需要在实施前明确。

## 10. 初始化方案

三张 public 配置表创建后，各插入固定 7 行。

三张配置表已各初始化 7 行。初始化时现有健康度表的说明和动作均为空，因此使用前端原有默认文案作为首次配置值；初始化本身未批量覆盖健康度表，只有组账号从前端保存时才执行正式同步。

## 11. 数据影响范围

保存规则会更新对应组内所有匹配 `customer_health_status` 的健康度记录，包括历史周期记录。不会修改：

- `customer_health_status` 本身；
- 客户健康分；
- 客户 ID；
- 周期起止日期；
- 销售金额；
- 拿货次数；
- 其他业务组的数据。

由于更新行数可能较多，实施前应先统计各目标表每种状态的影响行数，并在事务中执行。

## 12. 验收标准

1. 三张 public 配置表均只有指定 6 个字段，并各有且只有 7 种状态。
2. 前端始终按照“高活跃、活跃、稳定、观察、风险、流失预警、流失”展示。
3. 前端不能新增、删除、改名或排序客户状态。
4. 三个组账号只能读取和保存本组配置。
5. 修改达人组某一状态后，私域组和分销组配置及健康度表不变化；其他组同理。
6. 保存后 public 配置表对应记录的 `updated_time` 更新，`created_time` 不变化。
7. 对应组级、平台级和店铺级健康度表中，相同 `customer_health_status` 的 `state_instructions` 与跟进内容全部同步。
8. 更新后客户列表、客户详情和设置页重新查询即可显示新内容，不使用前端缓存的旧静态值。
9. 任一目标表更新失败时，public 配置表与其他已执行更新全部回滚。
10. 非法状态、缺少状态、重复状态或跨组请求被后端拒绝。

## 13. 已确认的实施结论

1. **跟进字段**：原字段名为笔误，统一使用 `follow_up_action`。
2. **同步范围**：同时更新对应组级表、平台级表与该组全部店铺级客户健康度表。
3. **主管端范围**：主管端不展示客户状态规则/客户健康度设置模块，只保留主管端原有的其他设置。

## 14. 实施与验证结果

- 三张 public 配置表已创建并核对：每张恰好 6 个字段、7 条固定状态。
- 后端自动化测试通过：固定顺序、组内权限、乱序拒绝、主管无规则且禁止保存。
- 前端构建和页面源码测试通过：固定 7 状态、后端 PUT 保存、主管端不展示保存入口。
- 真实接口联调通过：达人组读取 1 组 7 条；乱序保存返回 `HEALTH_RULE_STATUS_INVALID`；主管读取空组、保存返回 `SETTINGS_FORBIDDEN`。
- 真实数据库事务回滚验证通过：达人组 public 配置及组级、平台级、店铺级目标表在事务内同时可见，回滚后测试标记全部恢复，未遗留测试数据。

## 15. 平台级同步缺口修正

- 已修正原实现仅覆盖组级与店铺级、漏掉平台级表的问题。
- 达人组新增同步 `doudian.half_year_customer_health`；私域组新增同步 `youzan.customer_health_detail`。
- 已使用三张 public 配置表执行一次全量历史回填，共覆盖 14 张目标表。
- 回填后逐表核验结果：`state_instructions` 空值 0、`follow_up_action` 空值 0、与 public 配置不一致记录 0。
- 后续前端每次保存都会在同一事务内更新本组 public 配置表及该组全部组级、平台级、店铺级目标表。

## 16. 分销组保存性能优化

- 保存前对 public 原规则加行锁并比较，只保留真正变化的状态。
- 没有变化时直接返回，不扫描 `fenxiao`、`alibaba` 两张约 677 万行的大表。
- 非“流失”状态只更新变化状态，并通过两个在线创建的部分索引定位。
- “流失”单独使用全量更新路径，继续保证 public 与全部目标表同事务提交。
- 实测：分销组无变化保存约 `0.014 秒`；修改“风险”并同步 1,040 条记录约 `1.028 秒`。
- 性能测试使用事务回滚，测试标记在 public 和三张分销健康度表中的遗留数均为 0。
