# PR：AI 客户助手——经营诊断、证据解释与内部跟进建议

> 状态：已实施并完成自动验证，待用户页面审查
> 功能批次：AI 智能看板第 2 个功能
> 前置功能：AI 经营洞察已实施，前后端当前保持运行
> 数据库：沿用 PostgreSQL `weidian`；只读单个客户所属店铺 Schema 和对应 `public` 健康规则表
> 实施范围：客户详情页默认诊断、快捷分析、内部经营核查建议、现有客户分析上下文增强、测试与前后端重启验收

## 1. 功能目标

将现有客户详情页右侧“客户分析助手”从“用户必须先提问、上下文只有少量客户信息”的简单分析入口，升级为进入客户详情后自动生成的客户经营诊断助手。

### 1.1 产品定位修正

用户已明确本项目面向公司内部业务部门，不承担客服或客户沟通职能。因此本功能只回答“业务人员应该关注什么、核查什么、如何安排内部跟进优先级”，不考虑如何回复客户，也不生成任何面向客户的沟通文本。本 PR 中的定位高于旧需求文档里曾出现的“沟通话术”规划。

用户无需先输入问题，即可看到：

1. 客户当前健康状态及生效规则说明。
2. 本月、上一月、当前半年及上一半年的销售与拿货变化。
3. 主要商品和商品贡献集中度。
4. 可核对的数据证据、统计周期和来源表。
5. 跟进优先级和建议动作。
6. 支持业务人员按最近表现、健康依据、主要商品和店铺退款背景快速切换诊断视角。

本功能继续遵循“规则结果始终可用，配置模型后增强表达”的模式：

- 未配置 `api_key`：后端使用确定性规则生成客户诊断和内部跟进建议。
- 已配置 `api_key`：后端先生成规则证据，再调用模型增强经营诊断表达。
- 模型异常：自动降级为规则诊断，客户详情页保持可用。

## 2. 当前能力与缺口

### 2.1 当前已有能力

- 客户详情接口已经校验 `store_key` 是否属于当前账号权限范围。
- `CustomerService.detail()` 已读取客户身份、健康状态及日、周、月、季度、半年销售和主要商品。
- 客户详情页已经存在右侧 `ai-panel`、聊天记录、文本输入框和两个快捷问题。
- `/api/v1/ai/chat` 已支持当前客户上下文和最近 10 条有效历史消息。
- 当前登录角色可在设置页维护独立的 `base_url`、`api_key` 和 `model_name`。
- 未配置 AI 时，现有聊天接口会返回一段包含健康状态、半年销售额和拿货次数的简单文字。

### 2.2 当前缺口

- 进入客户详情后不会自动诊断。
- 现有 AI 上下文主要使用半年销售，没有上一周期对比。
- 证据和建议混在模型文字中，用户不能快速核对。
- 没有健康规则、健康快照日期和销售截止日期的一致性检查。
- 没有商品 Top1/Top3 集中度。
- 快捷问题只有“最近表现”和“主要商品”。
- 缺少面向业务人员的结构化核查重点和内部跟进优先级。
- 模型调用失败时，已配置 AI 的聊天接口当前会直接报错，没有客户助手专用降级结果。

## 3. 本 PR 范围

### 3.1 本次实现

- 新增 `POST /api/v1/ai/customer-analysis`。
- 进入客户详情后自动加载默认诊断。
- 增加月、季度、半年当前周期与上一周期对比。
- 增加主要商品及 Top1/Top3 金额集中度。
- 读取客户当前健康快照与所在组最新生效规则。
- 增加健康快照日期与销售截止日期一致性警告。
- 提供“最近表现、健康状态依据、主要商品、店铺退款背景、内部跟进建议”快捷入口。
- 内部跟进建议必须关联数据证据，只用于业务核查，不自动执行任何操作。
- 增强现有 `/api/v1/ai/chat` 的客户证据上下文和模型失败降级。
- 完成后运行测试并安全重启前后端，保持服务供用户审查。

### 3.2 本次不实现

- 不实现单客户退款金额或退款率。
- 不生成任何面向客户的回复、沟通话术、营销文案或客服文本。
- 不发送微信、短信、邮件或平台私信。
- 不自动修改客户健康状态、跟进记录或规则。
- 不自动创建优惠券、承诺折扣、库存或发货时间。
- 不跨店铺合并相同客户 ID 或昵称。
- 不新增商品名称、品类、库存、成本、毛利等数据库不存在的数据。
- 不新增 AI 审计和反馈数据库表；审计功能后续单独建立 PR。
- 不实现全局问看板和多智能体。

## 4. 数据库连接与权限范围

### 4.1 数据库

本功能继续使用项目根目录 `.env` 中 `DATABASE_URL` 指向的 PostgreSQL 数据库：

- 数据库名称：`weidian`。
- 后端连接入口：`8.11/backend/app/database.py` 的现有连接池。
- 前端不能直接连接数据库。
- 本功能所有业务查询均为只读，不新增迁移或数据表。

### 4.2 单客户所属店铺 Schema

每次请求只允许读取请求中 `store_key` 对应的一个 Schema：

| 业务组 | 店铺 Key | PostgreSQL Schema |
| --- | --- | --- |
| 达人组 | `weidian` | `weidian` |
| 达人组 | `doudian_children` | `doudianChildren` |
| 达人组 | `doudian_kocotree` | `doudianKocotree` |
| 达人组 | `kuaishou` | `kuaishouxiaodian` |
| 私域组 | `youzan_qijian` | `qijian` |
| 私域组 | `youzan_muying` | `muyinqijian` |
| 私域组 | `kuaituantuan` | `kuaituantuan` |
| 分销组 | `alibaba` | `alibaba` |
| 分销组 | `jushuitan` | `jushuitan` |

具体店铺 Key 以当前 `catalog.py` 中 `STORES` 的实际值为准；前端不能提交任意 Schema 名称，后端必须通过白名单映射得到 Schema。

### 4.3 使用的表与字段

| 诊断内容 | 表 | 过滤条件和主要字段 |
| --- | --- | --- |
| 客户身份及昵称 | `<store_schema>.customer_id_mapping` | `customer_id = %s`；昵称字段来自店铺目录配置 |
| 日销售 | `<store_schema>.customer_daily_sales` | `customer_id`、`transaction_date`、`transaction_amount` |
| 周销售及拿货次数 | `<store_schema>.customer_weekly_sales` | `customer_id`、周期、`weekly_transaction_amount`、`weekly_purchase_count` |
| 月销售及拿货次数 | `<store_schema>.customer_monthly_sales` | 当前月和上一月；`monthly_transaction_amount`、`monthly_purchase_count` |
| 季度销售及拿货次数 | `<store_schema>.customer_quarterly_sales` | 当前季度和上一季度；`quarterly_transaction_amount`、`quarterly_purchase_count` |
| 半年销售及拿货次数 | `<store_schema>.customer_half_year_sales` | 当前半年和上一半年；`half_year_transaction_amount`、`half_year_purchase_count` |
| 月度主要商品 | `<store_schema>.customer_monthly_product_sales` | 当前客户、当前月、金额 Top5 |
| 半年主要商品 | `<store_schema>.customer_half_year_product_sales` | 当前客户、当前半年、金额 Top5 |
| 客户健康快照 | `<store_schema>.customer_health_detail` | `customer_id`、`period_start <= as_of`；读取分数、状态、说明、动作、周期和更新时间 |
| 当前生效健康规则 | `public.talent_customer_status_action` / `private_customer_status_action` / `distribution_customer_status_action` | 根据店铺所属组和健康状态读取最新规则 |
| 店铺退款背景 | `<store_schema>.weekly_refunds`、`monthly_refunds`、`quarterly_refunds`、`half_year_refunds` | 只查询客户所属店铺周期汇总；不得描述为该客户退款 |

### 4.4 当前数据库明确不支持的内容

当前统一数据库没有稳定的 `customer_refunds` 表，因此不能回答：

- “这个客户退款了多少钱？”
- “这个客户的退款率是多少？”
- “这个客户为什么退款？”

用户询问此类问题时，系统必须明确说明“当前只有店铺周期退款汇总，无法归因到单个客户”。可以补充所在店铺的周期退款背景，但必须标注数据层级为店铺。

## 5. 后端接口设计

### 5.1 新增默认诊断接口

`POST /api/v1/ai/customer-analysis`

请求示例：

```json
{
  "store_key": "weidian",
  "customer_id": "customer-001",
  "as_of": "2026-08-11",
  "analysis_type": "overview"
}
```

### 5.2 支持的分析类型

| `analysis_type` | 页面入口 | 返回重点 |
| --- | --- | --- |
| `overview` | 进入详情自动执行 | 综合诊断、证据、风险和建议动作 |
| `recent_performance` | 最近表现 | 月、季度、半年销售及拿货变化 |
| `health_reason` | 健康状态依据 | 健康快照、规则说明、日期一致性 |
| `products` | 主要商品 | 月度/半年 Top5 和集中度 |
| `store_refund` | 店铺退款背景 | 所在店铺退款变化，明确非客户退款 |
| `follow_up` | 内部跟进建议 | 基于规则和经营证据生成业务核查优先级 |

### 5.3 响应示例

```json
{
  "code": "OK",
  "data": {
    "mode": "rule_summary",
    "configured": false,
    "degraded": false,
    "analysis_type": "overview",
    "conclusion": "客户近期销售回落，当前处于风险状态，建议优先跟进",
    "summary": "本月销售额较上一月下降，半年拿货仍有一定规模。当前健康状态为风险，建议先确认近期采购减少原因。",
    "evidence": [
      {
        "key": "month_sales_change",
        "label": "本月销售额环比",
        "value": "-18.0%",
        "period": "2026-08-01—2026-08-31",
        "source": "customer_monthly_sales",
        "description": "本月销售额较上一月下降18.0%。"
      }
    ],
    "actions": [
      {
        "priority": "high",
        "title": "优先确认采购减少原因",
        "description": "结合当前健康规则联系客户，确认近期需求变化。"
      }
    ],

    "store_key": "weidian",

```

### 5.4 现有聊天接口兼容

保留 `POST /api/v1/ai/chat` 的现有请求字段和 `answer` 返回字段，避免破坏当前页面；在兼容基础上增加可选的 `evidence`、`warnings` 和 `mode`。

聊天上下文最多保留最近 10 条有效消息。后端每次必须重新根据 `store_key + customer_id + as_of` 构造当前客户证据，不能相信前端历史消息中的数字。

## 6. 后端实现流程

### 6.1 权限与客户定位

1. 使用现有登录依赖获取 `current_user`。
2. 使用 `allowed_stores(current_user.role)` 校验 `store_key`。
3. 通过 `STORES[store_key]` 获取真实 Schema 和所属业务组。
4. 使用 `store_key + customer_id` 查询客户，不使用昵称作为主键。
5. 找不到客户时返回现有 `CUSTOMER_NOT_FOUND`。
6. 主管查看任意有权店铺客户时，健康规则按店铺所属业务组读取，不按主管角色读取。

### 6.2 客户证据快照

新增客户分析快照构造方法，复用现有 Repository，不复制第二套 AI 专用 SQL：

1. 读取客户身份和最新有效健康快照。
2. 读取月、季度、半年当前周期及上一周期销售与拿货次数。
3. 由后端计算变化额和变化率；上一周期为零时返回 `change=null` 和数据不足警告。
4. 读取当前月和当前半年商品金额 Top5。
5. 由后端计算 Top1 和 Top3 占当前客户周期销售额的比例。
6. 按店铺所属组读取当前健康状态对应的最新公共规则。
7. 比较健康快照 `period_end` 与销售统计截止日期；快照明显滞后时增加警告。
8. 只有 `analysis_type=store_refund` 或业务人员明确询问退款时才读取店铺退款背景。

### 6.3 确定性规则诊断

规则服务根据以下事实生成 `conclusion`、`evidence`、`actions` 和 `warnings`：

| 规则 | 判断依据 | 建议方向 |
| --- | --- | --- |
| 销售明显下降 | 月销售环比低于设定阈值 | 检查需求变化和近期采购中断 |
| 销售增长 | 月销售环比达到增长阈值 | 复盘主要商品和增长来源 |
| 拿货次数下降 | 当前月拿货次数低于上一月 | 判断金额变化是否由采购频次造成 |
| 高风险健康状态 | 风险、流失预警或流失 | 使用数据库当前规则提高跟进优先级 |
| 健康快照滞后 | 健康周期结束早于销售截止日期 | 提示状态可能未反映最新销售表现 |
| 商品高度集中 | Top1 或 Top3 占比较高 | 关注单品依赖并避免虚构替代商品 |
| 数据不足 | 上一期为零、缺表或缺少有效记录 | 不计算虚假变化率，明确说明缺口 |

规则阈值必须集中配置并写明注释，不散落在路由和前端。

### 6.4 模型增强

1. 根据当前登录角色读取现有 AI 配置。
2. 未配置时不调用外部模型，直接返回 `mode=rule_summary`。
3. 已配置时只向模型提供当前客户聚合证据、健康规则、分析类型和必要的业务问题。
4. 不向模型提供数据库连接信息、API Key、其他客户数据或完整内部配置。
5. 默认诊断中，模型只增强 `summary`；证据、数值和动作由后端规则控制。
6. 模型输出仅限内部经营分析，不得生成面向客户的回复或营销话术。
7. 模型失败时返回原规则结果，设置 `degraded=true` 并增加降级提示。

### 6.5 内部跟进建议规则

后端根据客户证据生成业务部门内部使用的核查建议：

| 经营信号 | 内部核查建议 | 禁止行为 |
| --- | --- | --- |
| 销售或拿货下降 | 核查下降周期、采购频次及主要商品变化 | 自动修改客户状态或编造下降原因 |
| 健康状态为风险类 | 按健康规则和客户贡献确定内部跟进优先级 | 把健康状态直接解释为确定事实 |
| 商品贡献高度集中 | 核查头部商品依赖和近期变化 | 编造商品名称、库存、价格或替代品 |
| 店铺退款上升 | 核查店铺级退款变化并标注数据层级 | 将店铺退款归因到当前客户 |
| 数据或快照滞后 | 优先核对数据日期和健康快照有效性 | 在数据不足时给出方向性判断 |

未配置模型时仍由确定性规则生成上述内部建议，模型只负责改善表达，不改变优先级和证据。

## 7. 前端交互设计

### 7.1 默认诊断

进入客户详情并成功加载客户数据后，右侧助手自动请求 `analysis_type=overview`。

面板结构：

- 顶部：助手标题、`规则诊断` / `AI诊断` / `已降级` 标签。
- 客户上下文：客户昵称或ID、店铺、健康状态、数据截止日期。
- 默认诊断：结论和2至4句摘要。
- 证据卡片：月销售变化、半年销售、拿货次数、健康状态、主要商品集中度。
- 建议动作：最多3条，展示优先级。
- 警告：快照滞后、上期数据不足或能力边界。
- 快捷操作：最近表现、健康状态依据、主要商品、店铺退款背景、内部跟进建议。
- 自由提问：保留现有输入框和聊天记录。

### 7.2 内部跟进建议交互

点击“内部跟进建议”后，请求 `analysis_type=follow_up`，按高、中、低优先级展示业务核查事项。每条建议必须展示触发该建议的指标或健康规则，不提供客户回复文本、复制话术或发送按钮，也不写入客户状态。

### 7.3 请求隔离

- 客户详情数据与 AI 默认诊断分别加载，AI 失败不影响客户详情。
- 切换客户、返回列表或改变截止日期时使用 `AbortController` 取消旧请求。
- 新响应必须同时匹配当前 `store_key`、`customer_id` 和 `as_of` 才允许展示。
- 快捷诊断响应和自由聊天记录分区展示，避免用户消息覆盖默认诊断证据。

## 8. 页面状态

| 状态 | 展示内容 | 是否影响客户详情 |
| --- | --- | --- |
| 加载中 | “正在分析当前客户数据” | 否 |
| 未配置 AI | 规则诊断、证据、动作和设置提示 | 否 |
| AI 配置可用 | AI 增强摘要，证据仍由后端生成 | 否 |
| 模型失败 | 规则诊断和“已降级”提示 | 否 |
| 客户无销售记录 | 显示身份/健康数据和销售数据不足说明 | 否 |
| 健康快照滞后 | 显示日期冲突警告，不强行解释 | 否 |
| 客户已切换 | 取消旧请求，不展示上一个客户结果 | 否 |
| 登录失效 | 沿用现有统一登录处理 | 由现有鉴权处理 |

## 9. 安全要求

1. 所有客户分析接口必须登录。
2. `store_key` 必须经过角色店铺白名单校验。
3. 数据库 Schema 只能由 `catalog.py` 映射，不能由请求直接指定。
4. 每次只查询一个 `store_key + customer_id`。
5. 模型不得看到 API Key、数据库凭据和其他客户数据。
6. 回答只能以普通文本渲染，不使用未清洗 HTML。
