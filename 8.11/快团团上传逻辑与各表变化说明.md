## 2. 已确认业务口径

### 2.1 日期口径

快团团全部业务表统一使用原文件中的`创单时间`确定业务日期：

```text
transaction_date = DATE(创单时间)
```

`支付时间`只作为原始字段保存，不参与`daily_sales`及其下游周期表的日期划分。

### 2.2 原始明细业务键

快团团文件中一行代表一个采购订单中的一个商品。数据库已有历史记录证明，同一个`子订单号`可能因为主商品、赠品而出现多行，因此不能只用`子订单号`去重。

最终业务键为：

```text
子订单号 + 商品编码
```

处理方式：

1. 数据库不存在该业务键：新增一条`raw_data`记录。
2. 数据库存在该业务键且任意上传字段变化：更新原记录，保留原`id`和`created_at`，更新`updated_at`。
3. 数据库存在该业务键且全部上传字段一致：标记为不变，不重复写入。
4. 同一文件内出现完全相同的业务键和内容：保留一条并报告文件内重复。
5. 同一文件内同一业务键内容不同：采用文件中最后一条，并报告文件内更新。

这套规则可以处理待支付记录后续变为已支付、退款金额变化、物流状态变化等场景，不会因为数据库中已经存在同一创单日期就跳过整日数据。

### 2.3 金额、数量、客户和退款口径

```text
交易金额 = 数量 × 商品金额
商品数量 = 数量
客户ID = 团长
退款金额 = 已退款+退款中
```

- `raw_data`原样保留文件中的待支付、已支付、已关闭、待发货、已发货、已取消等记录。
- 当前数据库历史`daily_sales`的541个日期均与“按创单日期汇总全部商品的数量×商品金额”完全一致，因此派生销售表继续沿用该口径。
- 取消商品通常数量为0，销售金额自然为0。
- 退款额独立统计，不直接从毛销售额中扣减。
- 商品编码为空或为`-`的记录保留在`raw_data`，参与整体销售和客户销售，但不进入商品维度表。
- 客户ID为空、`-`、`0`或`0.0`的记录不进入客户维度表；原始记录仍保留。

### 2.4 周期口径

- 自然周：周一至周日。
- 自然月：每月1日至当月最后一天。
- 业务季度：2—4月、5—7月、8—10月、11月—次年1月。
- 业务半年：2—7月、8月—次年1月。
- 周、月、季度、半年拿货次数：客户ID在`customer_daily_sales`中出现的日期数，即周期内有效创单天数。
- 同比、环比统一保留2位小数；没有可用对比值或对比值为0时写`0.00`。

## 3. 前端上传流程

### 3.1 文件选择

1. 私域组账号进入`#/private/upload`。
2. 在快团团卡片选择或拖入`.xlsx`或`.csv`文件。
3. 前端检查扩展名和文件大小，后端再次执行相同检查。

### 3.2 预览阶段

前端发送：

```text
POST /api/v1/uploads/sales
store_key=kuaituantuan
mode=preview
file=<用户文件>
```

后端执行：

1. 校验当前账号是否属于私域组。
2. 校验上传表头是否能映射到`kuaituantuan.raw_data`。
3. 检查必须存在`创单时间`、`子订单号`、`商品编码`。
4. 按`创单时间`解析业务日期。
5. 按`子订单号 + 商品编码`与数据库逐行比较。
6. 返回原始明细新增、更新、不变数量。
7. 返回新增客户数量。
8. 返回毛销售额、退款额及受影响的周、月、季度、半年。
9. 返回快团团、私域组、渠道三级金额预计变化。
10. 不修改数据库。

### 3.3 正式写入阶段

用户确认后再次上传同一文件，后端重新解析和校验。在一个数据库事务中依次执行：

```text
获取 kuaituantuan 上传锁
→ 新增/更新 raw_data
→ 补充 customer_id_mapping
→ 刷新 kuaituantuan 33张派生表
→ 获取 siyu、qudao 汇总锁
→ 刷新 siyu 11张表
→ 刷新 qudao 9张表
→ 校验刷新表数量和业务唯一键
→ COMMIT
```

任意一步失败，整个事务回滚。

## 11. `7.28.xlsx`上传性能优化

### 11.1 问题定位

`7.28.xlsx`包含1,983条商品明细。原实现虽然能保证正确性，但正式写入时会对每一条明细分别执行一次`raw_data`业务键查询。由于`raw_data`已有24万余条记录，这相当于对同一张原始表重复扫描1,983次。

事务内复现实测：

| 阶段 | 优化前耗时 |
|---|---:|
| 文件读取 | 0.001秒 |
| 文件解析及数据库差异判断 | 约1.4秒 |
| 1,983条原始明细写入 | 220.665秒 |
| 快团团33张派生表刷新 | 4.059秒 |
| 私域组11张表刷新 | 0.315秒 |
| 渠道9张表刷新 | 0.236秒 |

因此，长时间没有返回上传成功的直接原因是原始明细逐条查询，不是Excel上传、前端传输或53张派生表刷新。

### 11.2 优化方法

正式写入取得快团团店铺事务锁后，处理方式修改为：

```text
一次批量查询文件涉及的全部“子订单号＋商品编码”
→ 在内存中逐业务键判断新增、更新或不变
→ 批量插入全部新增记录
→ 批量更新全部变化记录
→ 刷新33张店铺表、11张私域组表和9张渠道表
```

事务锁仍然覆盖批量复查和写入过程，因此并发上传时不会产生重复业务键；原子提交、失败回滚和重复上传幂等规则均保持不变。

### 11.3 优化后复测

| 阶段 | 优化后耗时 |
|---|---:|
| 文件解析及差异判断 | 约1.8—2.4秒 |
| 1,983条原始明细写入 | 0.494秒 |
| 快团团33张派生表刷新 | 3.747秒 |
| 私域组11张表刷新 | 0.291秒 |
| 渠道9张表刷新 | 0.171秒 |
| 完整正式上传事务预计耗时 | 约7秒 |

原始明细写入由220.665秒下降到0.494秒，约提升447倍。复测在数据库事务中完成，最后执行回滚；回滚后`kuaituantuan.raw_data`仍为245,986条，其中2026-07-28仍为1,983条，确认没有残留测试变化。

另外模拟1,983条记录全部发生状态变化时，批量更新耗时0.505秒；说明优化同时覆盖“新日期首次插入”和“同一创单日订单/退款状态更新”两种日常场景。
