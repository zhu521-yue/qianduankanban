# 多平台销售上传模块

## 1. 目录边界

九个平台或店铺分别维护配置，公共解析、平台级日期策略预览和事务内基础写入逻辑只实现一份：

```text
upload/
├── weidian/
├── doudian_children/
├── doudian_kocotree/
├── kuaishou/
├── youzan_qijian/
├── youzan_muying/
├── kuaituantuan/
├── alibaba/
└── jushuitan/
```

各目录的`config.py`只保存Schema、交易时间字段、客户识别规则、客户名单字段、下游业务表和总体汇总链路。

## 2. 已确认的销售数据口径

销售导出文件是其所含交易日期的完整数据快照。因此，销售上传不再按订单号或商品明细键逐行判断新增、更新和未变化，而是按交易日期及店铺配置处理。已接入的抖店两店和快手使用`replace`：

- 数据库没有该交易日期：插入文件中该日期的全部销售记录；
- 数据库已有该交易日期：删除数据库中该日期的全部旧记录，再插入文件中该日期的全部最新记录；
- 一个文件同时包含新日期和重复日期时，分别新增和覆盖；
- 同一订单可以合法包含多条商品明细，销售文件不会按订单号合并或删除记录；
- 交易日期为空的行不参与销售日期快照，预览通过`excluded_undated_rows`单独报告。

其他店铺可配置`skip`：数据库已有的日期整日跳过，只插入不存在的新日期。快团团采用独立的`upsert`策略：业务日期取`创单时间`，以`子订单号 + 商品编码`作为商品明细业务键，已存在明细更新、缺失明细新增，不会因为同一创单日期已经出现就跳过整日数据。日期策略必须逐平台确认，不能由通用上传器猜测。

销售导出不是纯销售明细：文件中的退款状态必须一并保存到`raw_data`，并在同一批次刷新周、月、季度、半年退款表。销售额仍按有效销售状态统计毛销售额，退款额独立统计，不能直接从销售额中扣减。

后续独立退款文件采用不同写入策略：只能匹配并更新`raw_data`中已经存在的订单记录，不新增销售记录；匹配不到的退款记录进入异常审核。独立退款文件的字段映射和业务键仍需按平台另行确认。

## 3. 预览流程

1. 接收对应店铺导出的`.xlsx`或`.csv`文件；
2. 校验上传表头全部存在于该店铺`raw_data`；
3. 使用店铺配置的交易时间字段解析交易日期；
4. 保留所有具有有效交易日期的销售明细；
5. 查询文件日期在`raw_data`中的现有记录数；
6. 日期快照平台将已有日期标记为“覆盖”、不存在的日期标记为“新增”；快团团逐业务键标记为“新增、更新、不变”；
7. 识别文件中的客户并预检`customer_id_mapping`；
8. 对混合销售文件分别识别有效销售与退款记录；同一行允许同时进入毛销售额和退款额；
9. 计算受影响的日、自然周、自然月、业务季度和业务半年；
10. 读取店铺、平台、业务组和渠道的当前周期值，计算原值、本次差额和预计新值；
11. 返回预览，不修改数据库。

预览主要返回：

- `dates.new`：新增日期；
- `dates.replacement`：删除旧数据后覆盖的日期；
- `rows_to_delete`：正式执行时预计删除的旧记录数；
- `rows_to_insert`：正式执行时插入的完整销售记录数；
- `replacement_date_rows`：文件中属于覆盖日期的记录数；
- `excluded_undated_rows`：因没有交易日期而不进入销售快照的记录数；
- `business_preview.source_classification`：文件中的有效销售行、退款行、销售且退款行、毛销售额和退款额；
- `business_preview.store_period_changes`：店铺自然周、自然月、业务季度和业务半年的当前金额、文件金额、替换旧金额、差额及预计金额；
- `business_preview.aggregate_period_changes`：`doudian → daren → qudao`相同周期的逐层预计变化；
- `refresh.aggregate_tables`：需要刷新的平台、业务组、渠道具体表名，不再只返回Schema名称。

## 4. 事务内基础写入

`writer.apply_base_changes()`不会自行提交。调用方持有事务，并按以下顺序执行：

```text
获取当前店铺上传锁
→ 删除所有重复日期的旧raw_data记录
→ 插入文件内全部有效日期销售记录
→ 补充客户名单
→ 刷新店铺业务表
→ 刷新平台、业务组和渠道汇总表
→ 全链路校验
→ COMMIT
```

任一步失败必须回滚整个事务，不能出现“旧日期已经删除、新快照尚未插入”的部分成功状态。

## 5. 接口状态

- `mode=preview`：读取真实文件和数据库，返回新增日期、覆盖日期、预计删除/插入数量、客户名单和影响周期，不写数据库；
- `mode=commit`：抖店儿童服饰旗舰店、抖店Kocotree服饰配件店、微店、快手小店、阿里巴巴、聚水潭和快团团均已启用。快团团在单一事务中按商品明细键写入`raw_data`、刷新33张店铺派生表及20张`siyu → qudao`汇总表；任一步失败整体回滚；
- 快团团正式写入会在取得店铺事务锁后一次性批量复查全部`子订单号 + 商品编码`，随后批量新增或更新；禁止对每条明细重复扫描`raw_data`，以保证日常文件上传性能；
- 其余店铺的`mode=commit`仍由安全开关阻止，前端不显示正式写入按钮；
- 正式结果返回`write_result`和逐表`table_changes`，包含每张受影响表的原行数、新行数、新增、更新和删除数量；
- 默认文件上限为300MB。
